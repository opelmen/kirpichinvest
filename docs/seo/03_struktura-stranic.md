# Программная структура страниц: регионы, типы, авто, адреса, итоги

Дата: 11.10.2026. Опирается на то, что уже строит `build.py`, и на правило программного SEO: страница имеет право на индекс, только если у неё есть свои данные, которых нет у родителя и у соседей. Иначе noindex.

## Что уже есть

```
/                         главная
/torgi/                   вся страна, пагинация по 60
/torgi/{город}/           16 городов-миллионников (+100 км): таблица, FAQ, подборки, районы
/torgi/{город}/{тип}/     однокомнатные, доли, до 5 млн, повторные, дома, земля… при ≥ 3 лотах
/torgi/{город}/{район}/   районы и города-спутники при ≥ 2 лотах
/torgi/{регион}/          остальные субъекты из выгрузки (slug из market_feed.REGIONS)
/torgi/{регион}/{тип}/    при ≥ 3 лотах
/torgi/{тип}/             по всей стране: doli, doma, zemlya, kommercheskaya, bankrotstvo, arestovannoe…
/torgi/do-{1,2,3}-mln/    бюджетные подборки с пагинацией (проблема: 567 страниц)
/torgi/lot/{id}/          карточка, 16 594 активных + архив
/torgi/arhiv/             архив карточек
/byudzhet/, /analitika/, /slovar/, /stati/…, услуги
```

Это уже правильный каркас «хаб → регион → тип → карточка». Дальше три вещи: добить правила качества, добавить отсутствующие типы страниц и вынести авто.

## Правила индексации (применять ко всем спискам)

| Правило | Как сейчас | Как надо |
|---|---|---|
| Минимум лотов для индекса | 0 лотов → noindex; тип в городе ≥ 3, район ≥ 2 | Оставить. Добавить: регион с 1–2 лотами → noindex, follow (страница из одного лота не отвечает запросу «квартиры с торгов в области») |
| Пагинация | индексируется вся | Город и регион: индексировать. Бюджеты и общий /torgi/: страницы 2+ noindex, follow (лоты всё равно найдутся через город) |
| lastmod списка | дата сборки | max(lastmod лотов на странице) |
| Текст над списком | 1–2 предложения с цифрами | Оставить коротким. Не добавлять «SEO-тексты» |
| Сосед-ссылки | нет | 5–8 ссылок на соседние города/регионы по географии, 2–4 на статьи по контексту |
| Доля шаблонного текста | у карточки ≈ 70% | Цель ≤ 50%: данные вместо текста (см. карточку) |
| Сэмпл-контроль | нет | Раз в месяц 50 случайных страниц: читаем глазами, считаем, сколько «пустых». Больше 5% пустых — чиним шаблон, а не плодим страницы |

## Новые типы страниц по приоритету

### 1. Авто и спецтехника на torggid.ru/auto/ (приоритет A)

Сейчас авто живёт в приложении (app.torggid.ru/auto), которое закрыто от роботов. Это самая массовая категория торгов (≈ 25 тыс. лотов банкротов в год плюс ГИС Торги) и отдельный массовый спрос («авто с торгов», «конфискованные автомобили»). Структура по образцу недвижимости:

```
/auto/                        все авто, цифры: сколько лотов, медиана цены, доля с пробегом/VIN
/auto/{регион}/               регион
/auto/{категория}/            legkovye, gruzovye, avtobusy, spectehnika, pricepy, moto
/auto/{марка}/                toyota, kia, lada, kamaz… при ≥ 5 лотах
/auto/{регион}/{категория}/   при ≥ 3
/auto/lot/{id}/               карточка: марка, модель, год, VIN (если есть), пробег, фото с площадки, цена сейчас, этап, площадка, похожие
```

Данные из той же выгрузки `/api/v1/public/feed` с типом «авто» (сбор уже идёт, см. память «tech-catalog-plan»). Сборка той же `build.py`, вторая карта сайта `sitemap-auto-N.xml`. Статьи-спутники: «как купить авто с торгов», «снятие с учёта после торгов», «авто с торгов: что с ПТС и арестом». Срок: 2–3 недели разработки после согласования полей выгрузки.

### 2. Страницы «цена падает» (приоритет A, такого нет ни у кого)

Публичное предложение это 80% денег рынка. Запросы: «лоты с понижением цены», «когда снизится цена на торгах», «торги на понижение квартиры». Страницы:

```
/torgi/snizhenie-ceny/            лоты, у которых следующий шаг снижения в ближайшие 7 дней, сортировка по дате шага
/torgi/{город}/snizhenie-ceny/    то же по городу
```

Содержание: таблица «лот, цена сейчас, следующая цена, дата, площадка», и обновление три раза в день делает страницу живой. Данные `price_schedule` уже есть у части площадок (Фабрикант, PR #19 в zalog-desk). Где графика нет, лот не попадает. Ни у одного агрегатора в выдаче такой страницы нет.

### 3. Страницы улиц и адресов (приоритет B, хвост)

Люди ищут конкретный адрес, когда уже видели лот или живут рядом: «торги ул. Ленина 5 казань». Страница улицы собирает активные и архивные лоты по улице города: `/torgi/{город}/ulica/{slug}/` при ≥ 2 лотах за всё время (с архивом). Это длинный хвост с нулевой конкуренцией, по одному-два перехода на страницу, но тысячи страниц. Делать после авто: нужен нормальный разбор адреса (улица, дом) в выгрузке, сейчас `clean_address` даёт строку.

### 4. Итоги торгов: «за сколько продалось» (приоритет A по ценности, зависит от сбора)

Концепция P1.6 и план монетизации называют это главным активом, которого нет у конкурентов. Страницы:

```
/itogi/                       сводка: доля состоявшихся, медиана итоговой цены к стартовой по стране, по видам торгов
/itogi/{регион}/              по региону
/torgi/lot/{id}/              в архивной карточке: итог, цена, число участников, этап
```

Требует хранить результаты в сборе (сейчас есть `results.json` с SUCCEED по части лотов и `res_rows` на /analitika/). Как только данных станет больше 1 000 завершённых лотов, запускать. Это основа для ежемесячного «индекса торгов» (см. GEO).

### 5. Управляющие и организаторы (приоритет B, P2 концепции)

`/organizatory/{slug}/`: сколько лотов выставил, сколько состоялось, медиана итоговой цены к старту, регионы, активные лоты. Запросы «арбитражный управляющий Иванов торги» существуют, конкуренция нулевая, доверие высокое. Это B2B-страницы: управляющий сам придёт смотреть, что про него написано. Данные: поле организатора в извещениях есть у всех площадок. Делать после итогов.

### 6. Кадастровые кварталы (приоритет C, для профи)

ТБанкрот держит профи именно кварталами. Страницы `/torgi/kvartal/{номер}/` в поиск смысла не имеют (никто не ищет квартал словами), но как инструмент в приложении и «Охотнике» нужны. В SEO-структуру не включать.

## Карточка лота: как снизить долю шаблона

Не писать текст, а показывать данные. Что добавить в карточку из уже собираемого или дешёвого:
- История: когда появился, как менялась цена, какие этапы прошёл (lot_history уже хранит lastmod и статус, нужно хранить цену по датам).
- График публичного предложения таблицей с датами.
- Похожие объявления рядом (есть у части, `comps`).
- Итоги похожих торгов в регионе за последние 6 месяцев (после сбора итогов).
- Расстояние до центра города и район (по координатам, есть в приложении на карте).
- Одно фото с площадки с alt.

После этого блок «Что проверить перед заявкой» можно сократить до трёх пунктов со ссылкой на статью: он нужен человеку, но не должен быть половиной страницы.

- Статья → 2–3 города по контексту и 1–2 подборки типа: добавить.

## Карты сайта после PR #10

`sitemap.xml` → `sitemap-pages.xml`, `sitemap-catalog.xml`, `sitemap-lots-1..4.xml`. Добавятся `sitemap-auto-N.xml` и `sitemap-itogi.xml`. В Вебмастере и Search Console по каждой карте видно «загружено / в индексе»: это главный индикатор здоровья программных страниц. Норма через 2 месяца: карточки в индексе ≥ 60%, списки ≥ 90%.

## Чего не делать

- Не генерировать страницы «квартиры с торгов {город} {год}», «дешёвые», «недорогие», «без посредников» как отдельные URL: это дубли под синонимы, Яндекс склеит или накажет.
- Не создавать страницы регионов и подборок с 0–2 лотами ради ядра.
- Не писать ИИ-тексты по 300 слов на каждую подборку: пользы нет, риск есть. Цифры и FAQ из данных лучше.
- Не трогать URL карточек и городов: они уже в индексе и в 301 со старого домена.
